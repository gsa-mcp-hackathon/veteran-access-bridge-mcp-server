## What changed and who owns the remaining decision

**S14 — The local verifier now has an independent reference.** Previously two catalogs could agree on an altered description. The command now requires an independently selected full Git commit containing `eval/deepeval/approved-catalog.json`. It reads that committed object even if the working copy changes. It compares catalog membership, names, exact descriptions, structured schemas, annotations, security metadata, toolkit prefix, MCP binding and approved agent attachments. JSON object key order is immaterial. Missing approval or drift stops the command before it emits an acceptance result. The focused tests cover unchanged metadata, changed descriptions on one or both sides, schema and name changes, missing or duplicate tools, and binding drift. A test confirmed a downstream callback received no acceptance after rejection. The command itself has no dispatcher. [Verifier](../../eval/deepeval/verify_consolidated_configuration.py) · [Tests and CLI example](../../eval/deepeval/test_consolidated_configuration.py)

**Release owner:** approve the real catalog, binding and attachment set at a reviewed commit independently of the observed exports, and require that approval at the release gate. The checked-in YAML is exclusively an offline test fixture. Its 13 agent attachments do not describe the 21 attachments on the deployed agent. **IBM runtime owner:** provide a release-correlated pre-dispatch decision for a changed definition or identify the supported enforcement point. Approving a manifest or enabling a gate for IBM requires separate authorization. No source hash by itself grants approval.

**S13/A23 — Two notes now travel through an actual MCP tool-response channel.** The fixture exposes one in-memory `get_crm_case` read. The same scheduling preference appears in both results. The second note adds a harmless instruction to include a marker word. The SDK client received each distinct result with its untrusted-note label. Tests rejected an unknown case and an unregistered operation. The fixture has no database, external transport or model. The existing LiveKit test runner sends caller utterances, so typing the note into that runner cannot prove delivery as an IBM tool result. [Fixture](../../eval/deepeval/crm_result_fixture.py) · [Received results and content hashes](evidence/m64-remediation/s13-tool-results.json)

**Orchestrate environment owner:** authorize an isolated agent binding with fixture reads, no write destinations and a trace export for each arm. Acceptance requires the genuine tool result and call ID, IBM-selected tool names and arguments, a response grounded in the authorized facts, no unauthorized disclosure, and independent side-effect evidence. The marker trial establishes the local delivery mechanism only. It makes no claim about Avery's response to a privileged instruction.

**S15 — The open question belongs to IBM's outbound MCP client.** The existing binding export identifies the approved endpoint. The application-side VA redirect test exercises another client. IBM documents spans for connection retrieval, health checks and tool execution, and supports exporting an agent trace. Those sources do not establish credential handling at an unapproved destination for this instance. No untrusted endpoint was contacted and no new toolkit was registered. [IBM trace fields](https://www.ibm.com/docs/en/watsonx/watson-orchestrate/base?topic=agents-understanding-trace-details) · [IBM trace export](https://www.ibm.com/support/pages/exporting-watsonx-orchestrate-agent-trace)

**IBM transport or tenant audit owner:** provide sanitized, correlated approved and denied outbound decisions covering destination, registration state before and after, connection attempts and credential-forwarding disposition. A credential value is unnecessary. If such records require additional instrumentation, the owner must identify its scope and obtain explicit approval for an isolated environment. Tenant access to these fields remains unverified.

**S03/A21 — The case-link table is downstream of caller resolution.** On the dynamic path the trusted host checks the enabled roster and VA sandbox identity, derives a `VAB-CALL-` case from the voice session and provisions the request, case link, slot bindings and audit event. It can also create a synthetic patient if an exact persisted match is absent. The active session-to-case binding gates reads. The earlier zero matches on roster case IDs answered a different question. [Release resolver](https://github.com/gsa-mcp-hackathon/veteran-access-bridge-mcp-server/blob/main/src/veteran_access_bridge/services/sandbox_callers.py) · [Trusted host](https://github.com/gsa-mcp-hackathon/veteran-access-bridge-mcp-server/blob/main/src/veteran_access_bridge/app/trusted_voice_booking.py)

A read-only SELECT against the project's `vab_test` tables used the resolver's exact synthetic name and birth-date match. Of three enabled personas, two uniquely matched patients with existing appointments and one had no persisted match. Zero were ambiguous and zero unique matches had active calls. **Zero persisted roster patients qualified as unused and inactive.** This is a database snapshot, not a live identity check. [Qualification query](evidence/m64-remediation/s03-roster.sql) · [Aggregate result](evidence/m64-remediation/s03-roster-result.json)

**Fixture and trusted-host owners:** authorize two distinct unused sandbox personas in a disposable copy with approved inventory and normal identity checks. Scope approval to provisioning those two sessions, ordinary case and audit writes, and subsequent disposal of the copy. Start from a snapshot, correlate both session windows, IBM tool traces, MCP receipts and database observations, then discard the copy. Pre-seeding static roster case IDs would not reproduce dynamic routing. Existing appointments, CASE-048 and its approval are outside this plan. No seeding or calls took place.
