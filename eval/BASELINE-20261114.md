## What the 89 probes establish

For each of 21 tools: metadata presence, rejection of missing required arguments, rejection of an incorrectly typed required argument, and rejection/unavailability for an unknown reference. Five additional probes verify that durable-mode public mutations reject requests without trusted private authority. Denial checks compare application stores before and after the request to detect unexpected mutations.

These probes do not establish complete valid-input coverage, deployed authentication, cross-user isolation, prompt-injection resistance, or booking success. The planned functional and adversarial suites remain separate gates. Six VA source tools default to unavailable in this local setup; that is not evidence of live VA connectivity.

## DeepEval preparation and evidence policy

DeepEval 4.3.4 and MCP SDK 1.30.0 are isolated from application dependencies. The trace adapter requires actual inputs, outputs, tool arguments, protocol results, captured registry, runtime version, and schema commit. It rejects host-invoked calls as evidence of agent-selected tool use. Offline validation is the default; scoring requires an explicit model. Telemetry is disabled. No scoring or trace upload was performed.

Historical IBM evaluation runs remain historical. Do not score them against today's tool registry and label them current. A successful browser receipt does not by itself prove that IBM selected the MCP tool. The current named-model adapter also does not constitute a verified IBM judge integration.

## Remaining release and presentation gates

1. Freeze the current IBM agent's real traces and matching MCP registry; redact identifiers before any external scoring.
2. Complete valid-input functional coverage and the planned security families: authorization/isolation, identity/consent, replay, injection/tool trust, input/outbound controls, secrets, deployment/dependencies, and recovery.
3. Verify deployed versions, triage reachable dependency risks, repair and retest before release approval.
4. Run authorized isolated database acceptance and deployed latency checks. Do not create additional bookings under this evaluation preparation task.
5. Keep model scoring unmeasured until the user authorizes a provider and budget.

For judges, present three evidence views: **tool contract coverage**, **security gate outcomes**, and **a trace-linked synthetic booking demonstration**. Show numerators/denominators, skipped and blocked checks, commit identifiers, and evidence links. Avoid a single blended safety score or a claim of certification. This baseline is not yet the full planned evaluation.
